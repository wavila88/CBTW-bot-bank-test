# Tasks: Bank Test chat experience
Spec: ./spec.md
Test command: `npm test` (`vitest run`, from `front-bot-test-bank`) for the unit tests; `npm run test:e2e` for the automation test.

## How this spec is tested (decided by the developer)
- **One integration test, a journey that grows.** `e2e/chat-journey.spec.ts` holds a single Playwright test, "a customer holds a conversation", that walks the page like a customer would and checks many things along the way: it opens the page, sends a message, sends a follow-up and keeps talking in the same conversation. Each phase adds its steps to this same test (listed in the phase's "Journey" line); it is never split into many tests. It is an integration test: it uses **the real API** (no mocks), so the back end must be running with its CORS setting allowing `E2E_BASE_URL`, and it fails if the API is down. Because the model answers differently each time, the journey checks that an answer arrived, that the status is 200 and that the `conversationId` is chained between messages, never the exact text of an answer. It sends a few calls of the API's limit of 5 per minute per IP (3 in phase 2), so it is not run twice within a minute. The tests in `e2e/ask-a-question.spec.ts` stay as they are. The journey saves a screenshot at each phase's checkpoint (as a test attachment, not an assertion) for the developer to compare with `design/figma-frame-2-679.png`.
- **Unit tests (Vitest) only where there is logic**: one behavior each (Enter versus Shift+Enter, a blank message, the reducer's actions, safe rendering of the answer). A test that only asks whether a text, a title or a region is present has no logic and is not written: the journey already checks what is visible. They are quick and say exactly what broke.
- In each phase, step 1 (failing test) is the new journey steps plus the unit tests that have logic (a phase of static content has none); they must fail before the code is written, and pass in step 3.

Phase numbers start at 1 in each spec (a phase is named with its spec, e.g. "spec 002 phase 2"). Order decided by the developer: the look first (phases 1 and 2), then the behavior on top of that screen (phase 3). Every phase leaves the page working: a customer can still ask a question and read the answer, and `e2e/ask-a-question.spec.ts` keeps passing (the field keeps the accessible name "Your question" and the button "Send").

## How every phase is checked
- **The look** is compared by the developer with `design/figma-frame-2-679.png`, next to a Playwright screenshot of the page at 1440 × 1000 (the same way as spec 001 phase 2). Take the values from the real design with `get_design_context` (load the `figma-design-to-code` skill first); new values go to `src/shared/styles/tokens.css`, never hardcoded in a feature. HP-9 is checked in each visual phase for its area,.
- **Tests** as described in "How this spec is tested": the journey for what a customer does, unit tests for the small details. The look itself is verified by comparison, not asserted.
- **Architecture** (checked at each approval): the features are `shell` and `chat` in `src/features/`, each exposing only its `index.ts` and keeping its state with `createFeatureContext`; `app` composes them and passes data between them as props (a feature never imports another feature's internals); `shared` imports nothing from `features` or `app`; the HTTP calls go only through the shared client.

## Phase 2 — Ask in the real chat and read the answer in bubbles (covers HP-1, HP-2, HP-4, HP-7, HP-9, SP-1, SP-3, SP-6)
Result: the plain box is replaced by the designed chat. Header: the blue assistant icon, "Bank Test Assistant", the green dot with "Online · Available 24/7" and `ellipsis`. History: today's date separator and the assistant's welcome message with "Virtual assistant · time". Composer: the three static chips (a chip puts its text in the field and does not send it), the field with "Type your question here...", the disabled `mic`, the blue arrow button (Enter or the button sends, Shift+Enter adds a line), and the notes under it. Sending shows the customer's bubble on the right ("You · time") and the answer in an assistant bubble on the left, as plain text for now, in whatever language the API returns. A blank message sends nothing and says "Please type your question." An API error or an unreachable API keeps showing the notice spec 001 phase 4 already built (the API message with its reference, or "could not be reached"), and the customer can send again. The first answer's `conversationId` is kept in the chat state and sent with every following message; the API does the understanding of follow-ups such as "and in dollars?", the front only carries the id. The conversation lives only in memory (a reload shows the welcome state). This is the first use of `createFeatureContext`: the `chat` feature has its provider (messages, pending flag), composed in `AppProviders`.
Journey (adds to the same test, with the real API): sees the chat header and the welcome message; clicks a chip and sees its text in the field without a request going out; tries a blank message and sees "Please type your question." with no request; sends "How do I pay with my card abroad?" with Enter, checks that the request carried no `conversationId`, that the API answered 200 with one, and that the customer's bubble and the answer show; sends the follow-up "and in dollars?" and checks that its request carries the `conversationId` the first answer returned and that the API continues the same conversation; sends a message in Spanish and sees the reply as the API returns it; takes the second checkpoint screenshot. `e2e/ask-a-question.spec.ts` keeps passing.
Unit: `src/features/chat/` tests assert the reducer's actions (a sent message, an answer that keeps the `conversationId`, a failure, a blank message), Enter sends and Shift+Enter does not, a blank message calls nothing and shows the notice, an API error and a network failure show the existing notice, a chip fills the field without sending, and that the first request has no `conversationId` and the next ones send the one the API returned. The welcome message and the texts are not unit-tested (the journey sees them). The question tests that lived in `App.test.tsx` move to the chat feature, where that behavior now lives.
Manual check: ask about card payments abroad, then "and in dollars?", and see the answer follow the topic; ask one question in Spanish; compare the whole chat column with the frame (without the sample answer's steps).
