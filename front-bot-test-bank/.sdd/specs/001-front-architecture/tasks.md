## Phase 4 — A question reaches the API and its answer shows on the page (covers HP-6, SP-2, SP-3)
Result: in the browser, the page has a plain box to type a question and a button; sending it calls `POST /Chat` on the configured address through the shared client (`src/shared/api`) and shows the answer text on the page. If the API answers an error JSON, the page shows its customer message and trace id; if the API cannot be reached or answers something that is not JSON, the page shows a generic failure line. The client throws `ApiError` (status, message, trace id), `NetworkError` or `UnexpectedError`, never a raw exception. The backend allows the front's origin (CORS), set through an environment variable, with no hardcoded origin. This box is deliberately plain: spec 002 replaces it with the designed chat.
Test: `src/shared/api/client.test.ts` asserts, with the network call replaced, that a success returns the body, that an error JSON becomes an `ApiError` with its three fields, and that a network failure and a non-JSON answer become the two typed errors. `src/app/App.test.tsx` asserts, with the client replaced, that sending a question shows the answer, and that an API error shows its customer message and trace id. In the backend, a test asserts that a request from the allowed origin gets the CORS header and one from another origin does not.
Manual check: start the backend and the front (`.env.local` with the backend address); type a question in the browser and see the real answer; ask with only a space and see the API's message with its trace id; stop the backend and see the generic failure line; the browser console shows no CORS error.
